# Capacidades do Laravel 5.5 para a proposta de segurança

Pesquisa de documentação oficial, limitada à versão usada pela API na Etapa 02. Esta nota descreve mecanismos disponíveis; não afirma que o projeto já os aplica ou que uma correção foi testada.

| Necessidade | Capacidade documentada | Implicação para a proposta |
| --- | --- | --- |
| Autorizar cada operação sobre um evento | Policies agrupam permissões por modelo e podem ter métodos `view`, `create`, `update`, `delete` e outros nomes; devem ser registradas em `AuthServiceProvider`. A criação pode ser autorizada pela classe, sem instância. [Authorization 5.5](https://laravel.com/framework/docs/5.5/authorization#creating-policies) | Propor uma policy de evento com métodos explícitos também para suspensão, restauração, exclusão definitiva e upload. Registrar a policy e chamar a autorização em cada rota. Métodos extras são proposta de desenho, não implementação observada. |
| Negar requisições antes da mutação | O middleware `can` recebe a habilidade e o parâmetro de rota; o helper `$this->authorize()` no controlador lança exceção convertida pelo handler padrão em HTTP 403. [Authorization 5.5](https://laravel.com/framework/docs/5.5/authorization#authorizing-actions-using-policies) | Autorizar o evento carregado do banco **antes** de atualizar, apagar, restaurar ou armazenar arquivo. Testar o código HTTP e a ausência de efeito colateral. Para restauração, verificar como o projeto carrega modelos com soft delete antes de escolher middleware ou helper. |
| Exercitar permissões por perfil | Testes HTTP aceitam `get`, `post`, `put`, `delete`, `json`, cabeçalhos personalizados e `actingAs($user, 'api')`; respostas expõem `assertStatus` e verificações JSON. [HTTP Tests 5.5](https://laravel.com/framework/docs/5.5/http-tests) | Criar casos para anônimo, proprietário, convidado e usuário alheio, incluindo respostas 401/403 e payload sem dados indevidos. Confirmar separadamente se `actingAs(..., 'api')` funciona com o guard JWT concreto da API; se não, enviar um Bearer token fictício no teste. |
| Comprovar que negação não alterou dados | `RefreshDatabase` isola o banco de teste; `assertDatabaseHas`, `assertDatabaseMissing` e `assertSoftDeleted` verificam estado persistido. [Database Testing 5.5](https://laravel.com/framework/docs/5.5/database-testing) | Depois de cada 403, conferir proprietário, campos editáveis, `deleted_at`, convidados e estado de pagamento no banco. Usar somente base de teste descartável. |
| Testar upload sem gravar mídia real | `Storage::fake()` e `UploadedFile::fake()` permitem arquivos fictícios e verificações `assertExists`/`assertMissing`. [HTTP Tests 5.5 — Testing File Uploads](https://laravel.com/framework/docs/5.5/http-tests#testing-file-uploads) | Confirmar que upload negado não cria arquivo nem referência no banco; upload permitido deve respeitar tamanho, formato e associação ao evento. Se o caminho atual escreve diretamente fora de um disk configurado, haverá adaptação de código antes de usar o fake. |

**Limites da pesquisa:** a documentação descreve recursos do framework, não o comportamento do JWT de terceiros nem as políticas de produto. A matriz de quem pode ler dados de evento, localização e convidados ainda requer decisão explícita. Nenhum teste de integração ou correção foi executado nesta pesquisa.
